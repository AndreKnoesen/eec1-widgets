ENG6 Final Project: Cat 2 Grading Harness Specification

For: Rishad Joarder (primary; builds the harness), Basheer Ammar (data file format alignment), and the TA team (so student questions about test-harness expectations get consistent answers)

Purpose: This document is the interface contract between three things that have to fit together cleanly for Category 2 grading to run automatically:

  1. The reference dataset files that Basheer produces (per FinalProject_RefDataset_Procedure.md).
  2. The function signatures each student team must expose in their submitted code.
  3. The grading harness Rishad builds, which loads the reference data, calls the team's function, and produces the Cat 2 score row.

If any of the three drift from this contract, Cat 2 grading breaks. Read carefully, propose changes early.

Conventions Common to Both Tracks

  • All file paths inside the harness are absolute. Do not rely on cd or relative paths.
  • All times are stored as ISO 8601 strings ("2026-05-30T09:14:23") in JSON files and as MATLAB datetime objects after loading. The harness converts to elapsed seconds (relative to walk_start_time for Track A or sample 0 for Track B) before comparing to team output.
  • All .mat files use a single named variable. The variable name is fixed (see each track's section). Do not save extra workspace state into the same .mat.
  • Floating point comparisons use a tolerance defined in the harness (currently 1e-3). Students should not need to know this.
  • The harness runs on a clean MATLAB R2025a session with the team's submitted code folder on the path. No additional toolboxes beyond what MathWorks ships standard plus those used in MP1 to MP5.

Function the team must expose

function results = analyzeReferenceWalk(referencePath)

Input:
- referencePath (string or char): absolute path to a folder containing golden_gps.mat, golden_accel.mat, and golden_truth.json.

Behavior expected:
- Load the three files.
- Run the team's analysis pipeline (regime detection, floor detection, event detection, step counting) against the loaded data.
- Do not require any GUI interaction. The harness runs headless. If the team's primary workflow is in SensorDashboard.mlapp, factor the analysis logic out into class methods that this function can call directly.

Return: a struct with the following fields, exactly named:

Function the team must expose
Field Type Meaning
floor_at_checkpoints Nx2 array [time_seconds, predicted_floor] One row per ground-truth checkpoint. time_seconds is elapsed seconds from walk_start_time. The team must look up its predicted floor at each annotated checkpoint time.
detected_stair_events Mx3 cell or struct array with fields start, end, direction All stair events the team's detector flagged across the walk
detected_elevator_events Px4 with fields start, end, direction, floors_traveled All elevator events the team's detector flagged
gps_handoff_time scalar (elapsed seconds, or NaN if the team's app never switched regime) Time when the team's app first switched from outdoor to indoor mode
gps_handoff_lat scalar (degrees, NaN if not available) Latitude reported by the team's app at handoff
gps_handoff_lon scalar (degrees, NaN if not available) Longitude reported by the team's app at handoff
step_count integer Total steps detected over the entire walk

If the team's code throws an error or does not expose this function, the harness assigns 0 for the Cat 2 items that depend on it. The team can still earn the ThingSpeak record integrity 3 points (read directly from their channel).

Harness scoring logic (Track A)

For each metric in the Track A grading rubric Cat 2, the harness computes:

  • Floor detection accuracy (10 pts): for each row in floor_at_checkpoints, compare predicted_floor against the ground-truth floor at that same time. Score = 10 * (correct / total).
  • Stair event TPR (5 pts): match each detected_stair_events row to a ground-truth stair_events entry if the start times agree within 5 seconds. Score = 5 * (matched / total ground-truth stair events).
  • Stair false-positive penalty: count detected events that do not match any ground-truth event. Subtract 1 point for each 2 unmatched (rounded down). Floor at zero.
  • Elevator TPR (5 pts): same matching logic as stairs, applied to start AND end times (each elevator event has two anchor points).
  • GPS handoff (4 pts): convert gps_handoff_time to a clock time, compare against ground-truth entry_time. Compute distance from (gps_handoff_lat, gps_handoff_lon) to landmarks.main_entrance using a haversine. Apply rubric tiers (within 15 s and 20 m: 4; within 30 s or 40 m: 2; else 0).
  • Step count error (3 pts): absolute percent difference between step_count and total_step_count. Apply rubric tiers (10%: 3; 20%: 2; 40%: 1; else 0).
  • ThingSpeak record integrity (3 pts): harness directly queries the team's submitted ThingSpeak channel URL. Checks that all required fields (lat, lon, alt, floor, speed, accel magnitude, regime, walk ID) are populated and that sample density is at least one per 15 seconds during the walk window. Tiered: full / partial / missing.

Track B Interface

Reference data files (Basheer produces)

gesture_stream_1.mat and gesture_stream_2.mat

Each contains exactly one variable: accel_data. Type: Nx3 double matrix (X, Y, Z).

Sample rate is implicit and should be approximately 50 Hz (typical MATLAB Mobile rate). The harness reads the actual rate from a sidecar field in gesture_truth.json (see below).

gesture_truth.json

{
  "stream_1_shake_times_seconds": [<list of doubles>],
  "stream_1_duration_seconds": 90,
  "stream_1_sample_rate_hz": 50,
  "stream_2_duration_seconds": 60,
  "stream_2_sample_rate_hz": 50,
  "stream_2_shake_times_seconds": []
}

stream_1_shake_times_seconds is the list of times (relative to start of stream 1) at which Basheer performed deliberate shakes. The harness converts these to sample indices using the recorded sample rate.

Function the team must expose

function fired = testGestureDetector(referenceStream)

Input:
- referenceStream: Nx3 double matrix (X, Y, Z accelerometer samples).

Output:
- fired: logical column vector of length N. true at each sample where the team's gesture detector fires; false elsewhere.

Behavior expected:
- Apply the team's deployed gesture detector (the same one used in the running game) to referenceStream.
- The detector should not assume anything about the sample rate beyond the typical MATLAB Mobile range (40 to 60 Hz). If the detector uses a moving window, the window should be expressed in samples, not in seconds-via-an-assumed-rate.
- Do not require ThingSpeak or GUI to run. The detector class (GestureDetector or equivalent) must be callable headless on a buffer.

If the team's code throws or does not expose this function, harness assigns 0 for all gesture-detection items. The network round-trip test items can still be attempted independently.

Harness scoring logic (gesture detection)

The harness loads stream 1, calls testGestureDetector(stream_1.accel_data), then for each ground-truth shake time:

  • True positive: at least one true fires within +/- 1.0 seconds of the ground-truth shake. Latency = time from ground-truth shake to first true within the window.
  • False negative: no true within the window.
  • TPR: TP / 12. Score: 10 * TPR (rubric Cat 2 first row).
  • Median latency: computed over matched events. Score: 4 / 3 / 2 / 1 / 0 per rubric tiers (0.5 / 1 / 2 / 4 second thresholds).

Stream 2 measures false positives. Harness loads stream 2, calls testGestureDetector(stream_2.accel_data), counts true samples grouped into events (consecutive true samples count as one event). FPR = events / stream_2_duration_seconds. Score: 8 / 6 / 4 / 2 / 0 per rubric tiers (0.05 / 0.10 / 0.20 / 0.40 events per second).

Network round-trip test (Track B only)

Two items, 4 points each, in addition to gesture-detection scoring.

The harness expects the team's NetworkMessenger class to expose:

methods (Access = public)
    success = sendMove(obj, moveString)
    moves   = checkForRemoteMoves(obj)
end

Test 1 (write): harness instantiates the team's NetworkMessenger with their submitted ThingSpeak channel URL. Calls sendMove("HARNESS:tag"). Within 10 seconds, queries the channel directly via ThingSpeak REST API and confirms the entry appeared. Pass = 4 points.

Test 2 (read since last): harness writes two distinct tag moves directly to the team's channel through the ThingSpeak REST API (one per second). Calls team's checkForRemoteMoves(). Verifies both tags returned in the order they were written, with no duplicates. Pass = 4 points.

Template a team can copy

function fired = testGestureDetector(referenceStream)
    detector = GestureDetector();        % team's class

    N = size(referenceStream, 1);
    fired = false(N, 1);

    % If detector uses a moving window of W samples, slide it.
    W = detector.WindowSize;             % team-defined property
    for i = W:N
        window = referenceStream(i-W+1:i, :);
        if detector.detect(window)
            fired(i) = true;
        end
    end
end

(This is a reference implementation. Teams whose detector is event-based rather than per-sample can wrap differently as long as the returned fired is N-length and reflects detector output.)

Open Questions

  1. MATLAB version on the grader machine. Confirmed R2025a? If TAs grade on a mix of versions, behavior of poslog and accellog could vary slightly.
  2. Exact harness tolerance values. This spec uses 5 seconds for stair-event matching, 1.0 second for shake matching, and 1e-3 for floats. Tunable; flag if any feel wrong after dry-run.
  3. Team-side template distribution. Should the analyzeReferenceWalk.m and testGestureDetector.m template files be posted on Canvas alongside the project doc, or shown in Rishad's Workshop 2 (May 27)? Workshop 2 timing is tight relative to the May 18 to 24 isolation-build week.
  4. Failure-mode policy. If the team's analyzeReferenceWalk runs but throws partway through, do we score the metrics it returned before the crash, or zero out everything? Currently spec says: zero-out everything that depends on the function's return. Confirm.
