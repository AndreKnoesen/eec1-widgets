ENG6 Final Project: Cat 2 Test Harness Guide (Students)

Why This Document Exists

Your project is graded in part by an automated test harness. Category 2 of the rubric (30 of 100 points) is fully automated: the harness loads a reference dataset, calls a specific function in your submitted code, and computes scores from what your function returns.

If your project does not expose the right function with the right return format, those 30 points are unreachable regardless of how well your live app works.

Read this document before you write more than a skeleton, not the night before submission. Teams that build the test function early discover separation-of-concerns issues when there is still time to fix them. Teams that wait inevitably hit naming, signature, or path bugs at the worst possible moment.

What You Must Expose (Both Tracks)

A small testing function lives in your project's top-level folder. The function:

  • Takes a file path or a data array as input.
  • Runs your real analysis pipeline (the same code your live app uses) on that input.
  • Returns a struct or array in a specific format.

The harness expects the function file at the top of your submission folder so it sits on the MATLAB path when graders unzip your submission.

Track A: analyzeReferenceWalk(referencePath)

If you are on Track A, your submission must include a file named exactly analyzeReferenceWalk.m containing this function.

Signature

function results = analyzeReferenceWalk(referencePath)

referencePath is a string giving the absolute path to a folder containing three files:

  • golden_gps.mat (a single variable gps_data, a MATLAB timetable from poslog)
  • golden_accel.mat (a single variable accel_data, a MATLAB timetable from accellog)
  • golden_truth.json (an annotation file you do not need to write your own parser for; you only consume the data files)

What your function must do

  1. Load the two .mat files.
  2. Run your team's analysis pipeline on the loaded data: regime detection, floor detection, stair and elevator event detection, step counting.
  3. Build a return struct with the following fields, named exactly:
What your function must do
Field Type Description
floor_at_checkpoints Nx2 numeric array Each row: [time_in_seconds_from_walk_start, predicted_floor]. Times correspond to ground-truth checkpoint times the harness extracts from golden_truth.json; you predict your floor at each of those times.
detected_stair_events struct array with fields start, end, direction Times in seconds. Direction is "up" or "down". One entry per stair event your detector flags across the walk.
detected_elevator_events struct array with fields start, end, direction, floors_traveled Same structure, plus how many floors the elevator traveled.
gps_handoff_time scalar in seconds (or NaN if your app never switched regime) When your app first switched from outdoor to indoor mode.
gps_handoff_lat scalar (or NaN) Latitude reported by your app at handoff.
gps_handoff_lon scalar (or NaN) Longitude reported by your app at handoff.
step_count integer Total steps detected over the entire walk.

Important constraints

  • Headless. Your function must run without app.UIFigure or any other App Designer element. If your analysis logic lives inside callback bodies, you need to factor it out into class methods (per the MP5 separation-of-concerns principle) so this function can call it without launching the app. This is the moment when separation of concerns stops being abstract.
  • No ThingSpeak required for Cat 2. This function is offline-only. Your ThingSpeak integration is graded separately (Cat 1 reachability check, Cat 2 record-integrity check on your live channel).
  • Names matter. The harness reads return fields by exact name. A typo means zero on those metrics.

Template you can copy

function results = analyzeReferenceWalk(referencePath)
    % Load reference files
    gps_path   = fullfile(referencePath, 'golden_gps.mat');
    accel_path = fullfile(referencePath, 'golden_accel.mat');
    truth_path = fullfile(referencePath, 'golden_truth.json');

    S_gps   = load(gps_path);    gps_data   = S_gps.gps_data;
    S_accel = load(accel_path);  accel_data = S_accel.accel_data;
    truth   = jsondecode(fileread(truth_path));

    % --- TEAM CODE: drive your real analysis pipeline on this data ---
    % Example (adapt to your own class names and methods):
    analyzer = SensorDataAnalyzer();
    analyzer.processGPS(gps_data);
    analyzer.processAccel(accel_data);
    %
    % Then read out the values your harness needs:
    %   floor_predictions = analyzer.predictFloorAt(checkpoint_times)
    %   stair_events      = analyzer.getStairEvents()
    %   elevator_events   = analyzer.getElevatorEvents()
    %   handoff_info      = analyzer.getHandoffInfo()
    %   total_steps       = analyzer.getStepCount()
    % -----------------------------------------------------------------

    % Assemble the return struct in the EXACT format the harness expects:
    results = struct( ...
        'floor_at_checkpoints',     [], ...   % Nx2: [time_seconds, floor]
        'detected_stair_events',    struct('start', {}, 'end', {}, 'direction', {}), ...
        'detected_elevator_events', struct('start', {}, 'end', {}, 'direction', {}, 'floors_traveled', {}), ...
        'gps_handoff_time',         NaN, ...
        'gps_handoff_lat',          NaN, ...
        'gps_handoff_lon',          NaN, ...
        'step_count',               0 ...
    );

    % ... fill in fields from your analyzer's outputs ...
end

Self-test

You can test your function on your own data before any reference dataset is published:

  1. Run a short walk yourself with your app (any walk, even just down a hallway and back).
  2. Save the resulting gps_data and accel_data to .mat files manually (use the variable names above).
  3. Hand-build a minimal golden_truth.json with one fake checkpoint and one fake stair event so your function has something to load.
  4. Call analyzeReferenceWalk(yourFolder). Confirm it returns a struct with all the right field names and types.

If your function works on your own walk, it will work on the harness's golden walk.

Track B: testGestureDetector(referenceStream)

If you are on Track B, your submission must include a file named exactly testGestureDetector.m containing this function.

Signature

function fired = testGestureDetector(referenceStream)

referenceStream is an Nx3 double matrix of accelerometer samples (X, Y, Z columns). N varies (90 seconds at typical mobile sample rates is roughly 4500 samples).

What your function must do

Run your team's real gesture detector against the entire stream. Return a logical column vector of length N. The vector is true at each sample where your detector decides "a shake just fired here," and false elsewhere.

Important constraints

  • Same detector as the live game. This function must call your real GestureDetector class. If your live game tunes thresholds at runtime (with a slider, say), expose those tuned threshold values as class properties so the harness uses the same numbers your live game uses.
  • Sample-rate-tolerant. Express any window size in samples, not in seconds-via-an-assumed-rate. Mobile phone sample rates vary between roughly 40 and 60 Hz; the harness will not assume a specific rate.
  • Headless. No GUI, no ThingSpeak. Your GestureDetector must be instantiable and runnable on a buffer without anything else loaded.
  • Output length must equal input length. N samples in, N booleans out.

Template you can copy

function fired = testGestureDetector(referenceStream)
    detector = GestureDetector();        % your class

    N = size(referenceStream, 1);
    fired = false(N, 1);

    % If your detector uses a moving window of W samples, slide it:
    W = detector.WindowSize;             % expose this as a public property
    for i = W:N
        window = referenceStream(i-W+1:i, :);
        if detector.detect(window)
            fired(i) = true;
        end
    end
end

If your detector is event-based rather than per-sample, wrap it differently as long as the returned fired is N-length and reflects detector output at each sample.

Self-test

Record your own short stream and validate before the harness sees it:

  1. With MATLAB Mobile, log accelerometer for 30 seconds. During that 30 seconds, perform 5 deliberate shakes spread across the window. Note the approximate times you shake.
  2. Save the Nx3 matrix to a .mat file: save('myTest.mat', 'accel_data').
  3. Call fired = testGestureDetector(accel_data). Plot it: plot(fired);.
  4. Verify your fired vector goes true near each of your 5 shakes and stays mostly false between them.

If 5 of 5 shakes fire correctly with few false positives, your detector is in shape for the harness.

Track B Additional: Network Round-Trip Test

The harness also tests your NetworkMessenger class for ThingSpeak round-trip behavior. There is no separate function to expose; the harness uses your class directly.

So your NetworkMessenger must:

  • Accept your team's ThingSpeak channel URL via constructor argument or public property.
  • Expose public methods sendMove(moveString) and checkForRemoteMoves().
  • Be instantiable and callable without a running game. The harness creates the class, sends a test move, and reads it back; that needs to work outside any game state.

The harness will:

  1. Instantiate your class with your channel URL.
  2. Call sendMove("HARNESS:tag"). Verify the entry appears on your channel within 10 seconds.
  3. Write two distinct sequential moves to your channel directly (via the ThingSpeak REST API). Call your checkForRemoteMoves(). Verify both moves come back in the correct order with no duplicates.

If your class can pass these two checks on a quiet channel by itself, it will pass during grading.

Practical Advice

  1. Build the test function early. Implement analyzeReferenceWalk (or testGestureDetector) in Week 2 of the project, the same week you finalize your analysis classes. The act of writing this thin wrapper exposes separation-of-concerns issues immediately. You want to find them when you have time to fix them.

  2. Use the self-test before submission. Once the function works against your own walk or stream, you can submit your project knowing Cat 2 will execute cleanly. Teams that skip this step show up at submission with broken function paths or struct fields.

  3. Filenames are exact. analyzeReferenceWalk.m, testGestureDetector.m. Lowercase first letter, camelCase the rest. The harness uses the filename literally.

  4. Keep the function small. This file is glue: load files (Track A) or accept input (Track B), call your real classes, build the return value. The actual analysis lives in your classes. If your wrapper has more than 30 to 40 lines of substantive logic, you are doing too much in it; push that logic back into your classes.

  5. Headless means headless. If a grader cannot call your function without launching the App Designer GUI, the function fails. Test by running it in a fresh MATLAB session, from the command line, with your project folder on the path and nothing else.
