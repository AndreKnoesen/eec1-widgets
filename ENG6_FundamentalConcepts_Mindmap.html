Fundamental Programming Concepts: Study Mindmap

ENG 6 Cumulative Assessment | Companion to the Lecture Essentials Files

How to Use This Document

The Lecture Essentials files (one per lecture) tell you what was covered. This document tells you what it adds up to. The Cumulative Assessment is built around a small set of fundamental programming concepts that recur across nearly every problem in this course. This mindmap names those concepts, points to where you have already practiced them in lecture and lab, and gives you self-check questions that force you to put each idea in your own words.

Use this document the way you would use a coach, not the way you would use a checklist. For each of the seven nodes below, work through the self-check questions out loud or on paper. If your answer feels confident and specific, move on. If it feels vague, or if you find yourself reaching for a function name you have memorized rather than an idea you can explain, that node is where your study time will pay off most. The Lecture Essentials files and your Mini-Project work give you the worked examples; this document gives you the questions to ask yourself about them.

A note on the assessment itself: you have access to the full MATLAB documentation during the exam. The point of that access is not to make the exam easier. It is to make a specific kind of preparation futile. Memorizing function names will not help you. Recognizing the shape of a problem will.

Node 1. What kind of problem am I being asked to solve?

Why this matters. Every solution starts with reading. Before you can write a single line of code, you have to know what the inputs are, what the outputs should look like, what counts as a valid input, and what the program is supposed to do at the boundaries (empty input, no matches, extreme values). Most exam-time mistakes are not coding mistakes; they are reading mistakes. A student who solves the wrong problem perfectly still gets zero.

Where you have practiced this. Every Mini-Project handout begins with a specification: the function signature, the expected behavior, the test cases, and the edge cases. Pre-Lab and Post-Lab phases of MP1 through MP4 all start with the same skill of translating prose into a precise plan. The validation block in detectRapidAcceleration was written from a specification that listed exactly what counted as bad input.

Self-check.

  • Pick any Mini-Project function you wrote. Without looking at your code, write the function specification in three sentences: what it takes in, what it returns, and what makes an input invalid. Then compare to the actual handout.
  • Given a problem you have not seen before, what is the first thing you do before opening MATLAB? What questions do you answer first?
  • A specification says a function should return "the average of qualifying values." What questions do you ask before writing any code?

Node 2. What data am I working with?

Why this matters. Data has type and structure. A scalar behaves differently from an array; a logical behaves differently from a double; a row vector behaves differently from a column vector when you try to combine it with something else. Most "I don't understand why this errors" moments come from a mismatch between the type or shape of what you have and the type or shape that the operation expects. Floating-point arithmetic is also not exact, which creates a second class of surprises that look like bugs but are actually properties of the number system.

Where you have practiced this. The L1 floating-point trap (sqrt(2)^2 == 2 returning false), the question of what true + true returns, the L4 difference between data(:,1) (a column) and data(1,:) (a row), and the L5 trap where length(R) returns the column count for a wide matrix instead of the row count you wanted. The MP2 resultant calculation only works because each variable is a column vector of the same length, and a tiny shape mismatch produces an error that looks confusing but is fundamentally a data-shape problem.

Self-check.

  • Why is == almost never the right way to compare two computed floating-point numbers? Give one example where it gives the wrong answer, and explain in one sentence what you should use instead.
  • If you have a 500-by-4 matrix and you want a 1-D array containing just the third column, what shape is the result and how do you get it? What if you wanted the third row instead? What is the shape of that result?
  • What is the difference between a logical value and the integer 1? When does the distinction matter, and when does MATLAB quietly convert between them?
  • A function expects a column vector and you accidentally pass a row vector. What kinds of failures might result, and which of them are silent (wrong answer, no error)?

Node 3. How do I get the pieces I need from a larger collection?

Why this matters. Programs spend most of their time picking out parts of a larger thing: one element, a contiguous range, an end-relative position, an entire row or column, every element that satisfies some condition. The mental model is that a collection is an addressable sequence of values. The address can be a single number, a list of numbers, an entire dimension, or a logical condition that selects elements without naming positions explicitly. Once you have the right model, the syntax for any specific extraction is something you can look up.

Where you have practiced this. The MP2 dataAnalysis.m script extracts four signals from a sensor matrix using the column-extraction pattern (data(:,1), data(:,2), etc). The detectRapidAcceleration function in MP3 uses a logical mask to extract just the timestamps and magnitudes that exceed a threshold. The MP3 reflection asks why no single threshold works for every scenario, which is fundamentally a question about how predicate-based selection responds to changes in the threshold value.

Self-check.

  • Without using a for loop, how would you extract every element of a vector that is greater than the mean? Then, separately, how would you extract the corresponding positions rather than the values?
  • Given a 2-D matrix, how do you select the rows where the first column meets a condition, keeping all columns? Why does the same approach fail if you use the first row instead of the first column to define the condition?
  • When is the result of a selection a fixed size, and when does it depend on the data? What does that imply about how the next step in your code should be written?
  • A teammate writes data(data(:,1) > 2) intending to get the matching rows. Why does this not work, and what is the correct expression?

Node 4. How do I combine pieces into an answer?

Why this matters. Most useful programs are short pipelines of three universal operations. Transform applies an operation to each element of a collection and produces a collection of the same shape. Filter keeps only the elements that satisfy a condition. Reduce collapses many values into a single summary (a sum, a maximum, a count, an average). Counting events is filter then reduce. Computing the average of qualifying values is filter then reduce. Computing a peak time is reduce. Computing a running integral is transform then reduce. Recognizing the pipeline shape of a problem is the difference between a clear three-line solution and a tangled loop.

Where you have practiced this. The MP2 resultant computation is a transform: sqrt(Ax.^2 + Ay.^2 + Az.^2) applies the same operation at every position. Counting threshold-exceedances with sum(R > threshold) is filter followed by reduce. Finding the peak time with [~,idx] = max(R); peakTime = t(idx) is a reduce that produces both a value and a location. The dead-reckoning pipeline in MP4 (acceleration to velocity to displacement via two integrations) is two transforms in sequence. The detectRapidAcceleration body is a transform (compute the resultant), then a filter (keep events above the threshold), then a reduce (compute the average of those events).

Self-check.

  • Given a vector of measurements, describe in one sentence each how you would (a) double every value, (b) keep only the positive values, (c) compute the largest of the positive values, (d) count how many were positive. Which of those is a transform, which is a filter, which is a reduce, and which combines two of them?
  • A teammate writes a for loop that walks through a vector and adds up every element greater than zero. What is a one-line version of the same operation, and why is it easier to read and to verify?
  • When does the order of operations in a pipeline matter? Find an example where doing the filter before the transform gives a different result than doing the transform first.
  • Why is the two-output form of max ([val, idx] = max(R)) a more reliable way to find the time of a peak than locating the peak by value comparison?

Node 5. How do I express decisions in code?

Why this matters. Programs make decisions: if this, do that, otherwise do something else. The skill is twofold. First, building a correct condition (often by combining several simpler conditions with AND, OR, NOT, and parentheses). Second, picking the right control structure (binary branch, multi-way exclusive branch, dispatch on a discrete value, nested versus sequential checks). Most logic bugs are not syntax bugs. They are condition bugs (wrong combination, wrong operator, wrong boundary) or structure bugs (two checks that should have been one chain, or a single check that should have been two independent ones).

Where you have practiced this. The L6 boundary discussion (< versus <=) showed how a one-character change can put a value into the wrong category. The getColumn switch dispatch in L6 Activity 2 is a clean example of mapping a discrete input to a discrete output. The detectRapidAcceleration validation prologue chains several independent failure conditions, each with its own message and safe return. The avgA guard (if isempty(A); avgA = 0.0; else; avgA = mean(A); end) makes a binary decision based on whether anything was found.

Self-check.

  • What is the difference between two separate if blocks and a single if-elseif chain? Construct an example where they produce different behavior, and explain when you would want each.
  • In a condition that combines several tests, when must you use the short-circuit version (so that the right side is not evaluated when the left side already determines the answer)? Give an example where using the wrong form throws an error rather than producing a wrong answer.
  • A condition that uses an array where MATLAB expects a scalar is a common silent bug. Why is if R > threshold (where R is an array) almost never what you intend, and what should you write instead?
  • A specification says: "If the input is invalid, return safely. Otherwise, if the result is empty, return zero. Otherwise, return the mean." Sketch the control flow in plain English first, then in code. Are these checks dependent (nested) or independent (chained)?

Node 6. How do I package a solution that others (including future-me) can use?

Why this matters. A program is not just code that runs. It is code with a clear interface. Functions are the primary unit of packaging: inputs come in, outputs go out, and nothing else (no hidden coupling to whatever variables happen to be sitting in the workspace). A well-designed function is replaceable: if someone rewrites its body, code that calls it should not need to change. Object-oriented programming extends this idea by bundling related state with the methods that operate on it, and by deciding what is part of the public contract and what is private implementation. Both function design and class design are about boundaries: what is inside, what is outside, and what crosses the line.

Where you have practiced this. The L4 introduction of custom functions established the pattern: signature, doc comment listing inputs and outputs with size and type, body, end. The MP3 detectRapidAcceleration is a function with a clear contract: give me a sensor matrix and a threshold, get back timestamps, magnitudes, and an average. The MP4 SensorDataAnalyzer class shows the OOP version of the same idea: mobiledevConnection and rawData are private (no script can break them), TargetSignal and TargetSignalTs are public (scripts can read them safely without violating any invariant).

Self-check.

  • For any function you have written, list its inputs and outputs in plain language without looking at the code. Could a teammate use it correctly from your description alone? If not, your interface is unclear and the documentation in the function header is doing the wrong job.
  • Why is it bad practice for a function to read or modify variables that were not passed in as arguments? Construct a short example of a bug that this practice would cause.
  • For an object that represents accumulating state across multiple operations (a logger that records messages over time, a clock that ticks, a sensor analyzer that integrates twice), what goes wrong if the class is written so every method returns a new copy of the object instead of modifying the existing one? When would the copy-on-modification model actually be the right design?
  • For any non-trivial class, some properties should be private and some can be public. What is the question you ask yourself to decide which is which?

Node 7. How do I make my solution robust and know that it works?

Why this matters. A solution that produces the right answer on the input you happened to test is not a finished solution. The same code needs to behave predictably on inputs the writer did not anticipate: empty inputs, inputs containing NaN or Inf, inputs that violate a precondition, inputs at the boundary between two cases. Robust code either rejects invalid inputs with a clear message or returns a safe default that downstream code can recognize. Verification is the other half of the same skill: you do not actually know your code works until you have tested it against an independent reference, ideally one you computed by hand or analytically.

Where you have practiced this. The validation prologue in detectRapidAcceleration checks that the threshold is positive and finite, and that the sensor matrix has the right number of columns, exiting early with safe outputs if any check fails. The avgA = 0.0 contract on empty results is a deliberate design decision: NaN would propagate silently through downstream calculations, while 0.0 is the mathematically correct mean of zero events and is something callers can test for. The L8 cumtrapz verification (integrating a constant acceleration and checking that v(end) matches the analytical answer of 2 * t_end) is a model for how to build trust in a numerical pipeline before applying it to real sensor data.

Self-check.

  • For a function you have written, list at least three inputs that would be invalid (wrong type, wrong size, out of range, special values like NaN or Inf). What does your function do for each of them? Does it fail loudly with a clear message, or does it produce a wrong answer silently?
  • Why is returning NaN to indicate "no answer was meaningful" usually a worse design than returning a documented safe default? When might NaN actually be the correct choice?
  • Pick a numerical operation you have used in a Mini-Project. How would you verify that it produced the correct answer, using an example where you can compute the answer by hand or by a known formula? What test data would you choose?
  • If two integrations of a constant bias produce a result that grows quadratically over time, is that a bug in your code or a property of the method? How would you tell the difference?

A Final Word

The seven nodes above are not a list of topics to memorize. They are a list of questions you should be able to answer, in your own words, about your own work. If you can take any Mini-Project function you have written and walk through it using these questions ("here is the spec I was reading; here is the data I was working with; here is how I got the pieces I needed; here is how I combined them; here is how I expressed the decisions; here is the contract I exposed to the caller; here is how I made it robust"), you have internalized the structure that this assessment is built to measure.

The exam will not ask you to remember a function name. It will ask you to recognize the shape of a problem, choose an approach, and implement it cleanly. The Lecture Essentials files give you the raw material. This document gives you the questions to ask about that material. Together, they are the preparation.
